SECTION 2: PROBLEM ANALYSIS & SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
================================================================================

2.1 PROBLEM ANALYSIS
--------------------------------------------------------------------------------
Modern recruitment teams receive hundreds to thousands of resumes for a single
job requisition across inconsistent file formats (PDF, DOCX, DOC, TXT) and
diverse layouts. Manual resume screening suffers from:
  1. High Time Consumption: Recruiters spend 60-80% of screening time manually
     reading unqualified resumes.
  2. Keyword Bias & Inconsistency: Basic legacy ATS tools rely on naive exact
     keyword matching (e.g., failing to match "Postgres" with "PostgreSQL" or
     "React.js" with "React") and are easily gamed by keyword stuffing.
  3. Lack of Transparency: Black-box AI tools provide arbitrary scores without
     explaining why a candidate scored well or what skills are missing.
  4. Poor Handling of Edge Cases: Unparseable/corrupt PDFs often receive random
     or zero scores without alerting the recruiter, and freshers are unfairly
     penalized even for entry-level roles.
  5. Re-evaluation Friction: Changing job requirements or target roles forces
     recruiters to re-upload the entire candidate batch from scratch.

PROPOSED SOLUTION:
An Enterprise AI-Powered Applicant Tracking & Bulk Resume Screening System built
with FastAPI (Python), React 18 + Vite + Tailwind CSS, and a hybrid
deterministic-plus-semantic ATS Scoring Engine. It parses up to 50 resumes
simultaneously, supports 16 predefined industry roles (Option A) and custom job
descriptions (Option B), computes transparent 8-criteria configurable scores,
produces 6-category skill gap analyses, generates Google XYZ formula actionable
improvements, and allows one-click dynamic re-evaluation and CSV/Excel export.

2.2 FUNCTIONAL REQUIREMENTS (FR)
--------------------------------------------------------------------------------
FR-01: User Authentication & RBAC
  - System shall support user registration, JWT-based login, token refresh, and
    role-based access control (ADMIN, RECRUITER, VIEWER).
  - System shall gracefully handle session validation on ATS scoring routes.

FR-02: Dynamic Job Role Selection (Dual Input Modes)
  - Option A (Predefined Roles): Recruiter selects from 16 benchmarked roles
    (Software Engineer, Senior Full Stack Engineer, Java Developer, Python
    Developer, Frontend Developer, Backend Developer, Data Analyst, Data
    Scientist, Machine Learning Engineer, AI Engineer, DevOps Engineer, Cloud
    Engineer, Cybersecurity Engineer, Database Administrator, QA Engineer,
    UI/UX Designer).
  - Option B (Custom Job Description): Recruiter specifies Custom Job Title,
    Full Job Description, Required Technical Skills, Preferred Skills, Minimum
    Experience (years), Educational Qualifications, and Mandatory Requirements.

FR-03: Bulk Multi-Format Resume Upload & Parsing
  - System shall accept drag-and-drop bulk uploads of up to 50 resumes at once.
  - Supported formats: .pdf, .docx, .doc, .txt (up to 10MB per file).
  - Parser shall extract: Candidate Name, Email, Phone, Education, College /
    University, Graduation Year, Technical Skills, Programming Languages,
    Frameworks, Databases, Tools, Work Experience (years), Internships,
    Projects, Certifications, and Achievements.

FR-04: Extraction Failure Protection
  - If text extraction fails (empty, corrupt, or unparseable file), the system
    shall NOT assign a mock or fallback score; it shall set score = null,
    status = ERROR, and display an "Extraction Error" alert.

FR-05: Intelligent 8-Criteria Configurable ATS Scoring Engine
  - Compute ATS Compatibility Score (0-100) using default configurable weights:
      * Technical Skills Match    : 30%
      * Job Description Relevance : 20%
      * Relevant Experience       : 15%
      * Project Relevance         : 10%
      * Education Match           : 10%
      * Certifications            :  5%
      * Keywords Match            :  5%
      * Resume Quality (XYZ)      :  5%
      * TOTAL                     : 100%
  - Support semantic synonym matching (e.g., Postgres == PostgreSQL,
    K8s == Kubernetes, React.js == React, JS == JavaScript).
  - Apply Anti-Keyword Stuffing and Anti-Hallucination guardrails.
  - Apply Fresher Protection Rule (no experience penalty for entry-level roles).

FR-06: 6-Tier Score Classification
  - 90-100 : Excellent Match
  - 80-89  : Strong Match
  - 70-79  : Good Match
  - 60-69  : Moderate Match
  - 40-59  : Low Match
  - 0-39   : Poor Match

FR-07: 6-Category Skill Gap Analysis
  - For every candidate, categorize skills with evidence/reasons into:
    (1) Matching Skills, (2) Missing Mandatory Skills, (3) Missing Preferred
    Skills, (4) Partially Matching Skills, (5) Additional Skills, and
    (6) Relevant Technologies.

FR-08: Candidate Screening Results Dashboard
  - Display summary metric cards (Total, Avg Score, Shortlisted, Interview,
    Review Required, Low/Error).
  - Display ranking table with columns:
    Rank | Candidate | ATS Score | Skills Match | Experience | Status | Action.
  - Support real-time search (name/email/skill), multi-criteria filtering
    (score tier, skill, experience bracket, verdict), and sorting.

FR-09: Individual Candidate Report Modal (12 Sections) & Download
  - Clicking "View Report" displays contact header, overall score, 8-criteria
    breakdown, skill gap analysis, work/internship experience, education,
    projects, certifications, strengths, critical gaps, Google XYZ actionable
    improvements, and objective recruiter recommendation.
  - Allow downloading the report as a formatted .txt file.

FR-10: AI Recruiter Recommendations
  - Classify candidates into: Shortlist, Consider for Interview, Needs Further
    Review, or Not Recommended, with objective anti-bias reasoning.

FR-11: Dynamic Instant Re-Evaluation
  - When a recruiter changes the target role, custom JD, or weights after
    screening, the system shall allow instant re-scoring via POST /api/ats/rescore
    without requiring file re-uploads.

FR-12: Data Export
  - Export filtered/ranked screening results to CSV and formatted Excel (.xlsx).

2.3 NON-FUNCTIONAL REQUIREMENTS (NFR)
--------------------------------------------------------------------------------
NFR-01 (Performance):
  - Single resume evaluation shall complete in < 500ms in deterministic mode.
  - Bulk screening of 50 resumes shall process asynchronously without blocking
    the frontend UI thread, with real-time queue progress updates.

NFR-02 (Reliability & Fault Tolerance):
  - Automatic database fallback: If cloud PostgreSQL/Supabase is unreachable
    (2-second socket pre-check), backend auto-heals to local SQLite seamlessly.
  - Graceful AI fallback: If Gemini API key is absent or rate-limited, engine
    operates cleanly in high-performance deterministic-plus-semantic mode.

NFR-03 (Security):
  - Password hashing using bcrypt/passlib; JWT (HS256) bearer authentication.
  - Strict CORS origin policy, file extension validation, and 10MB file size cap.
  - Environment secrets isolated in .env (excluded from Git via .gitignore).

NFR-04 (Scalability):
  - Stateless FastAPI backend containerized with Docker and horizontally
    scalable via Docker Compose replicas / Kubernetes HPA (Horizontal Pod
    Autoscaler) + Celery/Redis async workers.

NFR-05 (Usability & UI Consistency):
  - Dark-themed enterprise dashboard with orange (#f97316) accent color,
    responsive layouts (desktop/tablet/mobile), and accessible color-coded badges.

NFR-06 (Maintainability & Testability):
  - Modular layered architecture (API Routes -> Core Engine -> Schemas -> DB).
  - Automated unit & integration test suite using Pytest (30/30 passing tests).

NFR-07 (Fairness & Anti-Bias):
  - Scoring relies strictly on objective skills, experience, projects, education,
    and measurable impact — ignoring protected personal attributes.

NFR-08 (Portability):
  - Cross-platform local orchestrator (scripts/setup-and-run.js) supporting
    Windows, macOS, and Linux, plus Docker images for cloud-agnostic deployment.

3.1 SYSTEM ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------
The system follows a 3-Tier Cloud-Native Microservice-Ready Architecture:

  1. Presentation Layer (Frontend SPA):
     - React 18, TypeScript/JavaScript, Vite 5, Tailwind CSS, Lucide Icons,
       Axios HTTP Client, React Dropzone.
     - Hosted on Vercel (CDN + Edge Rewrites) / Local port 8081.

  2. Application / API Layer (Backend REST API):
     - FastAPI (Python 3.10-3.12), Uvicorn ASGI server, Pydantic v2 schemas.
     - Core Modules:
         * backend/app/core/parser.py              (PDF/DOCX/DOC/TXT extraction)
         * backend/app/core/role_inferrer.py       (16 role benchmarks + custom JD)
         * backend/app/core/ats_scoring_engine.py  (8-criteria weighted engine)
         * backend/app/api/routes.py               (REST endpoints + CSV/XLSX export)
         * backend/app/core/auth_dependencies.py   (JWT, API Key, RBAC/ABAC)
     - Hosted on Render / Docker / Kubernetes (Port 8000 / 8080).

  3. Data & Infrastructure Layer:
     - Relational DB: SQLite (dev fallback) / PostgreSQL + pgvector (production).
     - Cache / Queue: Redis + Celery Workers (enterprise async processing).
     - Observability: Prometheus, Grafana, Loki, Promtail, Alertmanager.

3.2 CORE REST API ENDPOINTS
--------------------------------------------------------------------------------
  GET  /api/health              - System health & DB status probe
  POST /api/auth/register       - Register recruiter / admin organization user
  POST /api/auth/token          - OAuth2 JWT token authentication
  GET  /api/ats/roles           - Fetch all 16 predefined industry job roles
  POST /api/ats/score           - Evaluate raw resume text against JD or Role
  POST /api/ats/score-file      - Upload & score a single resume file
  POST /api/ats/bulk-screen     - Bulk screen up to 50 resumes simultaneously
  POST /api/ats/rescore         - Instant re-evaluation without re-uploading
  POST /api/ats/export-csv      - Export ranked screening dashboard to CSV
  POST /api/ats/export-excel    - Export formatted Excel (.xlsx) workbook

pipeline {
    agent any

    environment {
        IMAGE_VERSION   = "v2.1.${BUILD_NUMBER}"
        BACKEND_IMAGE   = "ghcr.io/vedanth-js/ai-ats-api"
        FRONTEND_IMAGE  = "ghcr.io/vedanth-js/ai-ats-frontend"

        stage('2. Backend Setup & Automated Tests (Pytest)') {
            steps {
                script {
                    if (isUnix()) {
                        sh '''
                            python3 -m venv .venv
                            .venv/bin/pip install --upgrade pip
                            .venv/bin/pip install -r backend/requirements.txt
                            .venv/bin/pytest backend/tests/test_ats_scoring_engine.py backend/tests/test_api.py -v --junitxml=backend/test-results.xml
                        '''

                        bat '''
                            python -m venv .venv
                            .venv\\Scripts\\pip install -r backend\\requirements.txt
                            .venv\\Scripts\\python -m pytest backend\\tests\\test_ats_scoring_engine.py backend\\tests\\test_api.py -v --junitxml=backend\\test-results.xml
                        '''
                    }
                }
            }
            post {
                always {
                    junit allowEmptyResults: true, testResults: 'backend/test-results.xml'
                }
            }
        }

        stage('3. Frontend Install & Production Build (Vite)') {
            steps {
                script {
                    if (isUnix()) {
                        sh 'npm install && npm run build'
                    } else {
                        bat 'npm install && npm run build'
                    }
                }
            }

            steps {
                script {
                    sh """
                        docker build -t ${BACKEND_IMAGE}:${IMAGE_VERSION} -t ${BACKEND_IMAGE}:latest ./backend
                        docker build -f frontend/Dockerfile.prod -t ${FRONTEND_IMAGE}:${IMAGE_VERSION} -t ${FRONTEND_IMAGE}:latest ./frontend
                    """
                }
            }
        }

        stage('5. Push Versioned Images to Registry') {
            when {
                branch 'main'
            }
            steps {
                withCredentials([usernamePassword(credentialsId: 'ghcr-credentials', usernameVariable: 'DOCKER_USER', passwordVariable: 'DOCKER_PASS')]) {
                    sh """
                        echo \$DOCKER_PASS | docker login ghcr.io -u \$DOCKER_USER --password-stdin
                        docker push ${BACKEND_IMAGE}:${IMAGE_VERSION}
                        docker push ${BACKEND_IMAGE}:latest
                        docker push ${FRONTEND_IMAGE}:${IMAGE_VERSION}
                        docker push ${FRONTEND_IMAGE}:latest
                    """
                }
            }
        }

        stage('6. Automated Deployment (Kubernetes / Cloud Hook)') {
            when {
                branch 'main'
            }
            steps {

10.3 TOP 10 VIVA QUESTIONS & CRISP TECHNICAL ANSWERS
--------------------------------------------------------------------------------
  Q1: Why did you build a deterministic-plus-semantic engine instead of relying
      100% on an LLM API like ChatGPT/Gemini?
  A1: Pure LLM calls suffer from non-deterministic score drift, API latency,
      hallucinations, and quota failures. Our hybrid engine guarantees
      reproducible 0-100 scoring, strict anti-hallucination guardrails, sub-500ms
      latency, and uninterrupted availability even when LLM APIs are offline.

  Q2: How do you handle keyword stuffing and missing/corrupt resumes?
  A2: Repeated keywords without project/experience context are dampened by our
      anti-stuffing guardrail. Corrupt or image-only PDFs where text extraction
      fails are never given fake scores; they return `overall_ats_score: null`
      and status `ERROR`.

  Q3: How does your Fresher Protection Rule work?
  A3: When the target role or custom JD specifies entry-level / 0 minimum years
      of experience, candidates with 0-1 years experience are not penalized in
      the 15% experience component and are evaluated fairly on skills, projects,
      internships, and education.

  Q4: How does Dynamic Re-Evaluation work without re-uploading files?
  A4: Extracted candidate profiles and raw parsed text are retained in client
      state and sent to `POST /api/ats/rescore` along with the new role, custom
      JD, or modified weights, immediately re-ranking all candidates.

  Q5: What major production bugs did you debug and solve?
  A5: (1) Docker/WSL IPv6 localhost hijack fixed by pinning proxy to 127.0.0.1;
      (2) W3C CORS wildcard+credentials violation fixed using regex origin rules;
      (3) 30s Supabase startup freeze fixed with a 2s socket pre-check that
      auto-heals to local SQLite; (4) Vite build syntax error in api.js fixed.

  Q6: Why use multi-stage Docker builds for the frontend?
  A6: Stage 1 uses Node.js to compile React/TypeScript into static assets, and
      Stage 2 copies only `/dist` into a lightweight Nginx Alpine image, cutting
      image size by >80% and reducing attack surface.

  Q7: How does Vercel communicate with the Render backend without CORS issues?
  A7: `vercel.json` defines edge rewrites mapping `/api/:path*` to
      `https://ai-ats-backend-yv1f.onrender.com/api/:path*`, so requests appear
      same-origin to the browser.

  Q8: How does Kubernetes ensure high availability for this ATS?
  A8: By running multiple replicas behind a ClusterIP Service, configuring
      liveness/readiness probes on `/api/health`, and attaching an HPA that
      auto-scales pods from 2 to 6 replicas when CPU exceeds 70%.

  Q9: How did you validate AI-assisted code during development?
  A9: Every AI-generated module was tested via 30 automated Pytest cases,
      verified with `vite build` for TypeScript/JS compilation, and manually
      smoke-tested end-to-end against live endpoints.

  Q10: How does JIRA integrate with your DevOps pipeline?
  A10: Every Git branch and commit message includes the JIRA issue key
       (e.g., `ATS-103`), automatically linking commits, GitHub Pull Requests,
       and Jenkins CI build statuses directly to the JIRA Scrum board.
